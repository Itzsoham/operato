How it works

Ask your restaurant a question. Here's what happens next.

Operato is a multi-tenant SaaS for restaurants, cafés and cloud kitchens. It covers the day-to-day work (menu, orders and tables, an inventory ledger, regulars, staff, a dashboard). On top sits an assistant that turns plain English into SQL and runs it against the restaurant's own data. The database, not the prompt, makes sure that SQL can only read and only sees one restaurant. This page walks through each flow in the app and how the code behind it is written.

Architecture

One path for almost every request

Next.js 16 App Router with React Server Components, Prisma 7 on Neon Postgres, and Better Auth. There is no middleware.ts or proxy.ts, and only one Server Action. Everything else follows the same path: a server page checks membership, a client component calls a typed React Query hook, and a guarded route handler validates the input and hands it to a service.

Multi-tenancy

The restaurant comes from the URL and nowhere else

One user can belong to several restaurants through RestaurantMember (OWNER, MANAGER or STAFF). The tenant id is read only from the [restaurantId] segment, and request bodies never carry it. The app's Prisma client owns the tables, so RLS doesn't bind it; isolation is enforced in layers instead.

Four layers

  • Pages: requirePageMember runs in the tenant layout and in each page. A non-member gets a 404, so the pages can't be used to probe which restaurants exist.
  • API: every tenant route is wrapped in withTenant, which returns 401 or 403. { roles } narrows it further.
  • Queries: every query filters on where: {'{'} restaurantId {'}'}.
  • Schema: composite "tenant-pinned" foreign keys, e.g. OrderItem → Order(id, restaurantId), so rows can't cross tenants even if a bug slipped through.

Take an order, cook it, take payment

  1. NewOrderDialog ("Pick the dishes, then send it to the kitchen.") calls useCreateOrder, which POSTs to orders/route.ts and then createOrder().
  2. In one transaction: prices are read from the menu (the client's prices are never trusted), availability is checked, the table is locked with FOR UPDATE, and GST at 5% is added as a Decimal. An atomic counter mints the order number ORD-0042, the lines are inserted with their unit prices snapshotted, and the table is marked OCCUPIED.
  3. Status moves go through PATCH, and only the transitions in ALLOWED_TRANSITIONS are accepted.
  4. payOrder() locks the order row, so the second of two racing tills gets 409 "already been paid". Only READY or SERVED orders can be paid. It sets PAID, rolls up the customer's totalSpend and visitCount, and frees the table if nothing else is open on it.
  5. Money mutations are never optimistic: the UI waits, toasts "ORD-0042 paid", then invalidates the orders, tables and customers queries.

A proper ledger, and warnings from real velocity

  1. useInventory reads getStockLines(): one SQL query that measures velocity as SUM(-delta) of outflows, then works out daysLeft and needsReorder.
  2. MovementDialog posts to applyMovement(), which locks the item with FOR UPDATE and computes a signed delta. An ADJUSTMENT is a stock-take (counted − balance). Taking out more than is on the shelf is refused.
  3. Each movement writes an InventoryTransaction with delta, balanceAfter, the user, and an autoincrement seq. Opening stock is a real movement too.
  4. STAFF can't post an ADJUSTMENT; that check is in the route handler.
  5. "AI stock alert" turns the reorder list into prose. If nothing needs attention it returns a canned message and makes no model call, and it falls back to a plain list if the model fails.

The Overview dashboard

  1. The server page loads the restaurant's timezone, then runs getOverview and getStockLines in parallel.
  2. Four KPIs (Revenue, Orders, Average order, New customers) compare the last 7 complete days with the 7 before.
  3. Also on the page: a reorder warning card ("Paneer (3d left)"), a 30-day revenue trend zero-filled with generate_series, the order-type mix, top sellers, and a "Known customers" meter.
  4. Every date boundary is computed in the restaurant's own timezone, not the server's.
WITH bounds AS (

)
SELECT CASE WHEN o."paidAt" >= b.today - make_interval(days => ${WINDOW_DAYS})
         THEN 'current' ELSE 'previous' END AS window,
       SUM(o."totalAmount") AS revenue, COUNT(*) AS orders
  FROM "Order" o, bounds b
 WHERE o."restaurantId" = ${restaurantId} AND o.status = 'PAID'

Ask a question, get the answer and the working

  1. AssistantClient validates the question (3–500 characters). useAskAi POSTs it to ai/query.
  2. The route loads the timezone and calls answerQuestion(), which runs these steps: rate limit → generate {'{'}sql, explanation{'}'} → sandboxed read-only run → serialize → a 1–4 sentence answer → an audit row.
  3. The UI shows the answer, an expandable SQL panel, a "sample of data" badge when the rows were truncated, and "X of 25 questions left today".
  4. Users only ever see AiError.safeMessage; Postgres errors become a 422 asking them to rephrase. The full safety design is below.

The Monday summary (Vercel Cron)

  1. vercel.json calls /api/cron/weekly-summary at 0 3 * * 1 (Monday 03:00 UTC). The route checks Bearer CRON_SECRET with timingSafeEqual and fails closed.
  2. runWeeklySummaries() walks the restaurants, skips any with a summary in the last 8 days, stops inside a 50-second budget, and reports whatever is left as remaining.
  3. For each restaurant it runs 6 metric queries in parallel for the last completed local week. If that week is already summarised it spends no quota. A week with no orders gets a fixed sentence and no model call.
  4. The result is upserted on @@unique([restaurantId, weekStart]), so re-running the cron is safe. The same run then checks that customer rollups haven't drifted from their orders.

Pro plan billing with Razorpay

  1. Checkout (OWNER only) reuses a pending subscription or creates one with notes: {'{'} restaurantId {'}'}. It never sets PRO itself.
  2. Browser: Razorpay Checkout opens with the subscription_id, and on success the page refreshes.
  3. Webhook: reads the raw body, checks the HMAC-SHA256 with timingSafeEqual, and only then parses it. Inside one transaction a ProcessedWebhook row (sha256 of the body) dedupes replays, and an ordering guard on planUpdatedAt ignores stale events.
  4. Backstop: a daily cron asks Razorpay for the real state and repairs any drift.

The billing code is built and unit-tested but not yet live-tested against Razorpay, and no feature is gated on the plan yet.

The AI boundary

A model-generated DELETE is impossible, not just unlikely

The rule the design follows: a SELECT-only check in the prompt is not security. The layers that actually hold are in Postgres. The code checks on top are there to fail early, with one exception covered below.

1
Rate limit

A rolling 24-hour count of AiQuery rows per restaurant; 25 by default, then 429. Failed attempts count too.

2
Structured generation

generateObject with a Zod schema {'{'}sql, explanation{'}'} at temperature 0. The model is never told the restaurant id.

3
Static pre-filter

assertLooksLikeSafeSelect: one statement, SELECT/WITH only, no comments or escapes, no forbidden keywords. Every quoted identifier must be on the allowlist.

4
Read-only role, read-only transaction

operato_ai_ro via DATABASE_URL_AI. SET LOCAL read-only mode, a statement timeout, and the tenant id; the query is wrapped in a LIMIT of 1001 rows.

5
Row-Level Security

14 tables use "restaurantId" = current_setting('app.restaurant_id', true). If the setting is missing, zero rows come back.

6
Answer + audit

At most 50 rows or 12,000 characters go back to the model for a plain-English answer. The whole exchange is recorded in AiQuery.

// inside the read-only transaction
await tx.$executeRawUnsafe(`SET LOCAL statement_timeout = '${STATEMENT_TIMEOUT}'`);
await tx.$executeRawUnsafe(`SET LOCAL transaction_read_only = on`);

Why the allowlist matters: in review, a quoted "set_config"(…) (or its Unicode-escaped form U&"\0073et_config") could re-point RLS at another restaurant. On Neon, set_config can't be revoked, so this code check is the real control for that attack. The code also re-reads the setting after the query and throws if it moved.

Least privilege, column by column

The AI role gets no blanket GRANT and no default privileges. It's granted an explicit list of 13 tables, then narrowed per column: no customer phone or email, no staff salary, and no auth tables, webhook log, AI log or summary tables.

Gemini, then OpenRouter

generateObjectWithFallback / generateTextWithFallback try gemini-flash-latest first. On any error they log and retry google/gemini-2.5-flash through OpenRouter. If both fail, the user gets a 503 with a safe message. Models are resolved at call time, so a missing key doesn't break imports.

Proven, not assumed

npm run verify:ai-boundary runs against the live database and checks that the role can't write, isn't a superuser and has no BYPASSRLS; that no table is readable without RLS; that the auth tables are closed; that RLS returns zero rows with no tenant set; and that both set_config payloads are rejected.

What the model is taught

lib/ai/schema-context.ts keeps a hand-curated column list for each table, written with satisfies ColumnsOf<typeof Prisma.XScalarFieldEnum> so that renaming a column breaks tsc. The prompt also carries enum values, a relationships block, and rules such as "never add a WHERE on restaurantId" and "revenue = SUM("totalAmount") where status = 'PAID', dated by "paidAt"". It ends with six worked examples ("What do I need to reorder?", "What time of day are we busiest?", …) that use a {'{'}{'{'}TZ{'}'}{'}'} placeholder for the restaurant's timezone.

How the code is written

The patterns that repeat

Zod at every boundary

There's one schema per route input in lib/validations/*, and the client form reuses the same schema. parseJson returns a result object instead of throwing; a failure becomes a 422 with fieldErrors keyed by path.

const parsed = schema.safeParse(body);
if (!parsed.success) return { ok: false, response: invalid(parsed.error) };
return { ok: true, data: parsed.data };
lib/api.ts · parseJson

Decimal money, serialized once

Money stays Prisma.Decimal end to end: const D = (v) => new Prisma.Decimal(v) and TAX_RATE = D("0.05"). It becomes a number only at the edge. The replacer reads this[key] because toJSON has already run by then.

JSON.stringify(value, function (this: Record<string, unknown>, key, val: unknown) {
  const raw = this[key];
  if (raw instanceof Prisma.Decimal) return raw.toNumber();
  if (typeof val === "bigint") return Number(val);
lib/serialize.ts

Row locks, in a fixed order

SELECT … FOR UPDATE on Order, Customer, RestaurantTable and InventoryItem, always in the same order (Restaurant → Table; Order → Customer → Table) so two requests can't deadlock. Transactions allow {'{'}maxWait: 8_000, timeout: 12_000{'}'}, inside the route's maxDuration = 30.

Errors that carry their status

Error classes carry their HTTP status: OrderError, InventoryError, AiError(status, safeMessage, {'{'}cause{'}'}), AuthError. Guards throw, and the route turns the error into a response. isUniqueViolation matches both Prisma's P2002 and Postgres's 23505.

React Query, keyed by tenant

Every query key starts with restaurantId. <SidebarInset key={'{'}restaurantId{'}'}> remounts the tree, so switching restaurants throws the cache away. Money mutations are never optimistic; menu categories and inventory updates are, with rollback. Defaults: staleTime: 30s, no refetch on focus, retry: 1.

Server-only by default

import "server-only" heads the db, auth, services and AI modules. Client code imports server types with import type only. Next 16 idioms throughout: params and cookies() are awaited, every route with real work sets maxDuration, and the React Compiler is on. Comments explain why: most files open with a rationale block.

Tests & tooling

The risky parts are the tested parts

Vitest: ~128 cases, pure logic

  • ai-sql-guard (39): stacked statements, data-modifying CTEs, pg_*, the set_config pivot, the identifier allowlist, breaking out of the LIMIT wrapper.
  • billing (24): HMAC signature, dedupe key, plan transitions, webhook schema.
  • ai-inventory-alert-rules (13) · ai-schema-context (12, PII never exposed) · validations (12).
  • ai-fallback (7): Gemini → OpenRouter · design-tokens (6).

Playwright: 15 end-to-end tests

  • auth: sign up → onboarding → dashboard; seeded sign-in; a vague error on a wrong password.
  • tenant-isolation: one owner gets 404 on another restaurant's pages and 403 on its APIs; no session gets 401.
  • order-pipeline: create → kitchen → pay → customer rollup; can't pay before the order is ready.
  • ai-assistant (model mocked): happy path, a 429 toast, the truncated badge.
  • billing-webhook: missing signature, tampered body, dedupe, replay.

Also: npm run lint (ESLint 9 flat config), npm run typecheck, npm run verify:ai-boundary, and a deterministic 90-day seed with two restaurants: Spice Garden and The Daily Grind. .claude/agents/ holds project-specific reviewer agents, including sql-safety-reviewer and security-reviewer.

Honest gaps

  • The AI limit is a flat 25 per restaurant per day; the landing page's "10 on Free" isn't enforced, and no feature is gated on the Pro plan yet.
  • Monday summaries are generated and stored, but no page shows them yet.
  • Selling an order doesn't deduct inventory (there's no recipe link), and there's no flow for inviting members.
  • Billing hasn't been live-tested against Razorpay, there's no CI workflow, and the app hasn't been deployed yet.
